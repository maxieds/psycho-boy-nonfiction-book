How to Fix 'Filename too long' Error in Git Clone & Resolve Permission Denied for core.longpaths

If you’ve ever tried to clone a Git repository and encountered the frustrating "Filename too long" error, you’re not alone. This issue is especially common on Windows systems due to historical limitations on file path lengths, but it can also surface on other operating systems in specific scenarios. Even more confusing: when you try to fix it by enabling Git’s core.longpaths setting, you might hit a "Permission denied" error.

In this guide, we’ll demystify both problems. We’ll explain why the "Filename too long" error occurs, how Git’s core.longpaths setting helps, and step through solutions to resolve both the path length issue and the permission errors that may block you from enabling core.longpaths. By the end, you’ll be cloning repositories smoothly—even those with deeply nested files.

Understanding the "Filename too long" Error#

The "Filename too long" error typically occurs when Git attempts to create a file or directory with a path that exceeds the maximum length allowed by the operating system or filesystem.

Why This Happens:#

  • Windows Systems: Historically, Windows imposed a MAX_PATH limit of 260 characters for file paths (e.g., C:\Users\YourName\Documents\project\...\file.txt). This includes the drive letter, colons, backslashes, and the filename itself.
  • macOS/Linux: These systems have much higher path limits (e.g., 4096 characters for Linux's PATH_MAX), so this error is rare but can still occur with extremely deep nesting or custom filesystem restrictions. Individual filenames on ext4 and most Linux filesystems are limited to 255 bytes.
  • Git’s Default Behavior: Git historically respected OS-level path limits to avoid compatibility issues, even if the OS could support longer paths.

What is core.longpaths in Git?#

Git includes a configuration setting called core.longpaths to bypass OS-level path length restrictions. When enabled (core.longpaths = true), Git allows longer file paths during operations like clone, fetch, or checkout.

  • Default Value: false (Git enforces OS path limits).
  • Scope: Can be set globally (for all repositories), locally (for a single repository), or temporarily during a clone.
  • Caveat: core.longpaths only affects Git’s internal handling of paths. It does not override the underlying OS or filesystem limits (though modern OSes like Windows 10/11 can be configured to lift their own restrictions).

Step 2: Address Windows OS Path Limitations (If Applicable)#

If you’re on Windows and still see the error after enabling core.longpaths, the OS itself may still enforce the MAX_PATH limit. Modern Windows (10 1607+, 11) lets you disable this limit:

Method 1: Use Group Policy Editor (Pro/Enterprise Editions)#

  1. Press Win + R, type gpedit.msc, and hit Enter to open the Local Group Policy Editor.
  2. Navigate to: Computer Configuration > Administrative Templates > System > Filesystem.
  3. Double-click "Enable Win32 long paths".
  4. Select "Enabled", then click Apply > OK.

Method 2: Edit the Windows Registry (Home Editions)#

  1. Press Win + R, type regedit, and hit Enter to open the Registry Editor.
  2. Navigate to: 
    HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\FileSystem
  3. Find or create a DWORD value named LongPathsEnabled (right-click > New > DWORD (32-bit) Value).
  4. Set its value to 1 (double-click the entry, enter 1 in "Value data").
  5. Restart your computer for changes to take effect.

Resolving "Permission Denied" When Setting core.longpaths#

If you encounter a "Permission denied" error when running git config --global core.longpaths true, it means Git lacks write access to its configuration files. Here’s how to fix it:

Permission Denied on Windows#

Common Cause: Git’s Global Config File is Protected#

The global Git config file (~/.gitconfig or C:\Users\<YourName>\.gitconfig) may be read-only or owned by a user without write permissions (e.g., if Git was installed as Administrator).

Fix 2: Adjust Permissions for .gitconfig#

  1. Navigate to your user folder: C:\Users\<YourName>.
  2. Find .gitconfig (it may be hidden; enable "Hidden items" in File Explorer).
  3. Right-click .gitconfig > Properties > Security > Edit.
  4. Select your user account under "Group or user names".
  5. Check "Write" under "Permissions for ".
  6. Click Apply > OK.

Alternative Solutions If core.longpaths Fails#

If enabling core.longpaths doesn’t resolve the issue, try these workarounds:

1. Clone to a Shorter Directory Path#

Use a shorter parent folder for cloning (e.g., C:\repo instead of C:\Users\YourName\Documents\Projects\OpenSource\Repos\...). Shorter base paths reduce the total length of nested files:

2. Update Git to the Latest Version#

Older Git versions had bugs with core.longpaths. Keeping Git up to date ensures you have the latest fixes. Update Git using:

  • macOS: brew install git (or brew upgrade git).
  • Linux: sudo apt update && sudo apt install git (Debian/Ubuntu) or sudo dnf install git (Fedora).
  • Windows: Download the latest Git for Windows.

3. Use a Different Filesystem (Advanced)#

If you’re on a Linux system with a filesystem that enforces short paths (e.g., FAT32), reformat the drive with a modern filesystem like ext4 or XFS, which support longer paths.

4. Use WSL2 on Windows (Advanced)#

Windows Subsystem for Linux (WSL2) runs a real Linux kernel and does not have the 260-character MAX_PATH restriction. Clone and work with repositories inside the WSL2 filesystem to avoid Windows path limits entirely. Note: cloning into the Windows-mounted filesystem from WSL2 is still subject to Windows path limits.

Conclusion#

The "Filename too long" error in Git is primarily a result of OS-level path restrictions, and Git’s core.longpaths setting is the primary fix. By enabling core.longpaths and adjusting OS or file permissions (if needed), you can clone even deeply nested repositories.

Key takeaways:

  • Use git config --global core.longpaths true to enable long paths globally.
  • On Windows, lift the MAX_PATH limit via Group Policy or Registry.
  • Resolve "Permission denied" by running terminals as admin (Windows) or fixing .gitconfig ownership (macOS/Linux).
  • For persistent issues, use shorter clone directories or update Git.
